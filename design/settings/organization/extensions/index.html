Added by issue #33 — the same class of gap as the four surfaces that issue lists, and the one it did not: ADR 025 built this page and recorded its own drift ("no wireframe exists for this surface"), and the shipped org-settings sidebar has had an "Extensions" item with no mockup to match. The item is new in the sibling pages' sidebars here for the same reason. Built and real, and admin-only. The trust warning, the acknowledgement copy, the status badge, the upload rules and the "this is exactly what runs" source view are the component's own words. What makes this page different from every other settings page, and why the warning comes first: an uploaded extension is arbitrary code running inside the job container with the agent's own access — the project's GitHub installation token and the model API key — so enabling one is not a configuration change but a decision to run somebody's code with the organization's credentials. That is why the acknowledgement gates the upload button rather than sitting beside it as a formality, and why a full source view exists at all. Not mocked: the empty state ("No extensions uploaded."), the loading state, the success/failure notices, the delete confirmation, the disabled-while-busy states, and the upload validation message (draftBundleIssue: a missing name, a missing entry path, or an empty file set). The file editor shows one file where the real form renders one textarea per file plus "Add file" and "Remove". Nothing here is proposed.

Extensions

Pi extensions your organization has uploaded. These are arbitrary code: a project only loads them if it opts in.

⚠ An extension is arbitrary code. It runs inside the job container with the same access as the agent itself: it can read the pod’s environment — including the project’s GitHub installation token and the model API key — make network requests, modify the workspace, and emit tool calls that Yggdrasil treats as the job’s real result. There is no sandbox. Only upload code you have read and trust.
