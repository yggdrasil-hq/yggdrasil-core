Wireframe · maps to /settings/organization — a new route/page, no equivalent exists in web/ today. IA rework round 3: top hub-header replaced by the same persistent sidebar as every other page (see /projects's design-note for the full rationale). Introduces a new Organization/Membership/Role data model that ADR 002 explicitly deferred ("Team RBAC and multi-user project permissions (Phase 2)" — see ADR 002 follow-ups, and roadmap/phases.md: "RBAC, team invitations — not started, no team/org entity exists yet"). This wireframe treats projects as belonging to an org (not directly to owner_user_id as ADR 002 currently has it) — that's the load-bearing assumption behind everything on this page and needs its own ADR before being built. Two more existing decisions this proposes to supersede: (1) ADR 003 §4 — "One target Kubernetes cluster per Orchestrator instance for MVP. No multi-cluster credential routing... yet" — the Kubernetes cluster section below moves that from an instance-level deploy-time env var (KUBECONFIG_HOST_PATH etc., deploy/.env) to org-level in-app config, which is exactly open-questions.md #10 ("multi-cluster credential routing"), now being answered rather than left open. (2) ADR 007 — per-user default model configuration, decided because "there is no team/org entity yet" (ADR 007 context) — the Providers & Models section below moves that to org-level, admin-managed, which obsoletes account-level model config as anything other than a read-only view — now reconciled: /settings/account is read-only (links here for anyone who can actually edit), and both the project-creation wizard (step 3) and project-settings' model card now resolve against this organization's models instead of a personal account default. ADR 007 itself still needs a full rewrite or replacement — its central premise, "no team/org entity yet," no longer holds once this ships. Role permission matrix below is a proposed starting point, not derived from any existing spec — five roles (Admin/Developer/Designer/Product Manager/Tester) were given from the request; the specific capability grants are my best-effort default, flag anything that should change. All data faked, all controls except the two CSS-only toggles ("Viewing as," invite reveal) are inert.
