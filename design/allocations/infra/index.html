Wireframe · maps to /allocations/infra (web/app/allocations/infra/page.tsx → components/allocations/infra-allocations-page-client.tsx). Built, and rendering real data with real effect — corrected by issue #50: ADR 030 decided these caps, so the page reads fetchOrganizationAllocations and writes per project via setProjectResourceQuota. Two things about this note were wrong beyond the missing route. It said "org-admin-only in concept": the write is admin-only, but ADR 030 item 14 deliberately made the read member-visible — a cap is the operational fact explaining why a project's work stopped, not a credential, and hiding it from the developer who is blocked turns "you are over quota" into an unexplained failure. And it said there was no decided enforcement mechanism: ADR 030 item 11 is precisely that the Orchestrator now applies the quota to the project's namespace ResourceQuota (an update path, merged into the existing Hard map, where before it was written once at namespace creation and never revisited), so Kubernetes enforces these rather than Yggdrasil. What's grounded: ADR 003 §5–6's one-namespace-per-project isolation is the natural scope for a per-namespace ResourceQuota, exactly as this page assumes. What's still not: ADR 003 never specifies real CPU/memory numbers, so the platform defaults remain the fallback for a project with no row (ADR 030 made the ADR 003 §17 defaults configurable rather than inventing numbers here), and no LimitRange is added — every job pod declares requests/limits explicitly, so one would be redundant (ADR 030 item 12). The mock's cluster-capacity and live-utilisation cards do not ship: no mechanism to expose live cluster telemetry exists or is decided, and ADR 030 item 18 keeps it out of scope rather than faking it. 'Save changes' is per-row in the real page, not page-level: with real projects a single save would issue N writes that can partially fail and leave the page showing a state the API does not have.
