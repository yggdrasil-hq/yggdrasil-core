Wireframe · maps to /infrastructure — a new route/page, no equivalent exists in web/ today. Org-only, per the request — it's a read-only status view of the same cluster /settings/organization's Kubernetes cluster section actually configures (kubeconfig, ingress class, cert issuer, apps domain all sourced from there). More grounded than Usage/Analytics: the architecture concepts shown are real — ephemeral per-job pods, one Kubernetes namespace per project as the isolation unit (not per-tenant, not per-repo), a sandboxed container RuntimeClass (gVisor/Kata) applied universally as defense-in-depth since job pods hold a live scoped GitHub token, dedicated node pools explicitly deferred out of MVP scope — all straight from ADR 003 §5–7. What's not grounded: there's no decided mechanism for the API/Orchestrator to expose live cluster telemetry to the Web app at all — CPU/memory gauges, per-pod resource usage, a live "active jobs" list are all new capabilities this page assumes exist, not documented anywhere. The "Resource limits" table is illustrative only — ADR 003 never specifies actual CPU/memory request/limit numbers; don't treat these as real defaults.
