Corrected by ADR 032 item 3: "Resume from here" is back, with a different meaning. The third correction above — that it was gone — was true when written and is not any more. ADR 024 item 1 scoped out a control that would have been a second way to do what the reply composer already does; ADR 032 item 3 built a true fork instead: a dispatched spec_grill job restores an earlier run's stored Pi session into a new pod and branches it at a chosen entry. So the block above is a picker, not a per-turn control — the points are Pi's own get_fork_messages list, and attaching them to bubbles would mean comparing user-message *text*, the weaker second reading ADR 032 item 2 exists to avoid. The rewind stays per-turn beside each bubble and the two are deliberately not visually symmetric, because the thing a reader has to tell apart is whether the conversation survives: the rewind says everything after the chosen turn is discarded, this one says the conversation is kept and the spec is rebuilt from that reply (an approved ADR stops being current, which matters — the terminal submit_adr overwrites the ADR, so a surviving approval would let a build launch against a document nobody approved). What is still not mocked: the control's real conditionality. It appears only where the API would accept it — a conversation turn (agent_text / ask_user / user_message, and the API enforces the same set), a spec_grill job, a feature still in draft / spec_ready / failed / cancelled, and not a run that is still going. Every turn here happens to be restartable, so the mock cannot show the negative case — on a feature that has moved past Spec (this page reached via Implementation or Testing, say) the page renders with no restart controls at all. Nor is the "this session was restarted from an earlier message" notice mocked, which is what a run produced by a rewind shows in place of the discarded turns.

ADR: Saved payment methods

Context
Customers re-enter card details on every purchase. Repeat customers should be able to save a card.

Decision

Tokenize cards via Stripe SetupIntent. Store payment_method id + last4/brand only. Add a default_payment_method_id on the customer record, allow marking one card default. Removing the default requires picking a new one first.
